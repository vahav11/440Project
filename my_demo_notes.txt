=====================================================
1. THE SCHEMA        (show schema.sql)
=====================================================

SHOW: scroll through the 4 CREATE TABLE blocks.
      then in Workbench: SHOW TRIGGERS FROM comp440;

SAY:
"Four tables. user from Phase 1, then item, item_category
 and review.

 Categories get their own table because the assignment says
 an item has one or more categories. That's a list, and a
 list can't go in one column. One row here is one category
 on one item.

 The primary key is both columns together, so the same
 category can't be added twice to an item, but the same item
 can appear many times with different categories.

 In review, UNIQUE (itemID, reviewer) enforces one review per
 item per user in a single line. The rating is an ENUM of the
 four allowed values, so an invalid rating can't be stored."


=====================================================
2. THE TRIGGERS      (still in schema.sql)
=====================================================

SAY:
"Some rules can't be a constraint, because a constraint only
 sees the row being inserted. Counting how many items someone
 posted today needs to look at other rows. Checking if you own
 an item needs to look at another table. So those are triggers.

 Each one checks something before the insert and calls SIGNAL
 to refuse. The message in SIGNAL is what the user sees in red."


=====================================================
3. PART 3 - REVIEWS
=====================================================

SHOW, in this order:

  Browse Items
    -> left list is  SELECT DISTINCT category FROM item_category
       nothing hardcoded, it's whatever is in the data
    -> click a category, that's a JOIN of item and item_category

  Click Reviews on an item you DON'T own
    -> ratings tally, existing reviews, the form

  Submit a review           -> works
  Review the same item again -> "already reviewed this item"  (UNIQUE)
  Open your OWN item         -> form is hidden
  Write 3 reviews, try a 4th -> blocked  (trigger)

SAY:
"The user only types two of the five values. The item, the
 username and the date come from the app, not from them.
 If they could type their own username they could review as
 somebody else.

 We don't check the four rules in Python. The database already
 enforces them, so the code just tries the insert and shows the
 error if it's refused."


=====================================================
4. QUERIES 3, 5, 6      (Store Reports tabs)
=====================================================

SAY FIRST:
"All three of mine are 'for all' questions. Every review is
 Excellent or Good. Every review is Poor. Never got a Poor
 review.

 SQL has no FOR ALL. So you flip it: instead of proving it's
 true for everything, you prove no counterexample exists.
 That's NOT EXISTS."


Q3  - input a username
      SHOW: an item of theirs with a Fair review is NOT in the list
      SAY: "Two conditions. EXISTS checks the item has at least
            one review. NOT EXISTS checks none of them is Fair or
            Poor. Without the EXISTS, an item with no reviews
            would pass, because with no reviews there's no bad
            review either."

Q5  - no input
      SHOW: the returned user's reviews are all Poor
      SAY: "Only needs one subquery. Reading FROM review already
            guarantees they wrote at least one."

Q6  - no input
      SHOW: a returned user who owns an item with ZERO reviews
            and an excluded user who owns an item with a Poor
      SAY: "The requirement says items with no reviews should
            still count as passing, and we wrote nothing for
            that. An item with no reviews never appears in the
            inner query, so it can't disqualify anybody.
            A join would have got this wrong, because it would
            have dropped those items entirely."
